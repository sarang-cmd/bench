5. Screen and input model

  • Layout: title bar at the top, content in the middle, softkey bar at the bottom.
  • Softkeys: F1 to F6 match labels in the bottom bar, as on the stock OS.
  • Keys: arrows move, EXE confirms, EXIT goes back, MENU leaves the add-in.
  • Redraw: draw a full frame, then update the screen. Redraw on key press only. Pacer redraws once per second.
  • Palette (Bauhaus): paper #f4f3ee, ink #2f2d2e, red #d92d27. Convert to the 16-bit color format in theme.h.
  • Home screen: five tiles with a square, circle, triangle, half circle, and bar. Plain shapes, no animation.

Text entry is the hard part. The calculator has an ALPHA shift. Spike M1 tests letter entry. Fallback: choose files from a list and avoid typing names. Search uses a short field with ALPHA input.

6. Tool specs

6.1 Pacer

Inputs: total minutes T, total marks M.

Math:

  • mpm = T / M minutes per mark.
  • Checkpoints every C marks, default 10. Checkpoint k sits at k * C * mpm minutes.
  • While running: you press F1 to log marks done d at the current time t.
  • Target marks at time t is t / mpm.
  • Gap in minutes is (t / mpm - d) * mpm = t - d * mpm. Positive means behind.

Screens:

  1. Setup: two number fields, checkpoint size.
  2. Plan: mpm, checkpoint table.
  3. Run: big clock, marks logged, gap line, next checkpoint time.
  4. Done: total time, final gap.

Acceptance tests:

TMmpmCheckpoint at 10 marks
90801.12511.25 min
1201101.090910.91 min
600error line, no next screennone

Edge cases: zero or empty input, marks above 999, pause and resume, clock reaches T.

6.2 Uncertainty

Represent each quantity as value and absolute uncertainty. Use double for math and a custom formatter for output. Do not depend on float printf until the spike proves float printing works.

Operations:

OpValueUncertainty
A + Ba + bda + db
A - Ba - bda + db
A * Ba * babs(result) * (da/abs(a) + db/abs(b))
A / Ba / babs(result) * (da/abs(a) + db/abs(b))
A ^ na^nabs(result) * abs(n) * da/abs(a)
k * Ak * aabs(k) * da

Chain mode: the result becomes A for the next operation.

Rounding (setting, default 1 significant figure for uncertainty):

  • Round the uncertainty to 1 significant figure. Use 2 if the first digit is 1. Make this a setting.
  • Round the value to the same decimal place as the uncertainty.
  • Use half-up rounding on the decimal digits, not on the binary float.

Show on screen: result, absolute uncertainty, percentage uncertainty.

Acceptance tests:

InputExpected
(10.0 ± 0.1) + (5.0 ± 0.2)15.0 ± 0.3
(2.0 ± 0.1) * (3.0 ± 0.1)6.0 ± 0.5
(4.0 ± 0.2) ^ 216 ± 2
(10.0 ± 0.1) / (4.0 ± 0.2)2.5 ± 0.2 (raw 0.15, half-up)
A with value 0 in a producterror line, no crash

Edge cases: zero value, negative values, uncertainty larger than value, tiny and huge exponents.

6.3 Cards

File format, one card per line:

What is the unit of impulse? | N s

Rules: split at the first pipe. Trim spaces. Skip blank lines and lines starting with #. Limit 500 cards per deck and 120 characters per side. Show a warning for longer lines.

Leitner boxes: three.

  • New cards start in box 1.
  • Right answer: box + 1, capped at 3.
  • Wrong answer: box 1.
  • Session draws from box 1 first, then box 2 every second session, then box 3 every fourth session.

Screens: deck list, session (question, EXE to reveal, F1 right, F2 wrong), summary, stats per box.

Progress file maps a card id to a box. Card id is a hash of the question text, so edits to the answer keep progress. Edits to the question reset the card.

Acceptance tests:

  • Quit and relaunch keeps every box.
  • Editing an answer keeps the box. Editing a question resets the box.
  • A file with 500 cards loads and runs.
  • A file with a bad line shows the line number and skips the line.

6.4 Notes with Markdown

Viewer features: file list, scroll, page jump, search, jump to heading list, back to list.

Supported Markdown subset:

SyntaxRender
#, ##, ###Heading levels, color and size
**bold**Bold style
*italic* or _italic_Italic style
code in backticksMonospace span
Fenced code blockMonospace block, no wrap
- or * bulletsBullet with indent
1. listsNumbered with indent
> quoteLeft bar and indent
---Horizontal rule
[text](url)Show text only
- [ ] and - [x]Box and check marks

Not supported in v1: tables, images, HTML, footnotes, nested lists beyond 3 levels. Show these as plain text.

Math: show $...$ as plain text. A converter in tools/md2bench.py replaces common symbols with ASCII or glyphs the font covers.

Parser design:

  1. Read the file into one buffer. Cap 32 KiB at first. Raise the cap after the memory spike.
  2. Split into lines. Classify each line into a block type.
  3. Parse inline spans inside each block with a small state machine. No recursion.
  4. Layout: measure word widths with the font, wrap to the screen width, and produce an array of display lines. Each display line holds span records: offset, length, style.
  5. Render only the visible display lines.
  6. Scroll position is a display line index. Rewrap on font change.

Style plan, two phases:

  • Phase A: no extra fonts. Use color and underline. Headings use red or ink with a rule. Bold uses the ink color on a light highlight bar. Italic uses an underline.
  • Phase B: generate bold, italic, and monospace fonts with fxconv. Swap styles through theme.h.

Search: case-insensitive substring. F-key jumps to the next match and highlights the line.

Encoding: the loader reads UTF-8. Characters outside the font map to ? and the viewer lists a count in the footer. md2bench.py rewrites known symbols first.

tools/md2bench.py tasks:

  • Replace smart quotes, dashes, and ellipses with ASCII.
  • Replace unsupported symbols from a mapping table.
  • Strip front matter, HTML tags, and image lines.
  • Report every change and every unsupported block.
  • Write the output into a folder ready to copy.

Acceptance tests:

  • A note with every syntax row renders each row correctly.
  • A 30 KiB note scrolls without visible lag.
  • Search finds a word on the last line.
  • A file with a missing glyph shows ? and the footer count.
  • An empty file shows an empty state, not a crash.

6.5 Number theory

Limits: unsigned 64-bit math, inputs up to 18 digits. Reject larger input with an error line. The SuperH compiler has no 128-bit integer, so write mulmod with 32-bit limbs or double-and-add.

05

FAQ

01Which OS should you run for the IB?

Run the newest Casio OS. Casio lists version 3.81 as the current fx-CG50 update, and its IB page points fx-CG50 users to 3.81. Your 3.80.0212 sits one step behind.

The IB expects the approved OS on your calculator in the exam room. Update at home, weeks before your first paper. Check the version under Menu, System, F4 Version.

02Is flashing a different OS possible?

Official Casio OS files install. I found no public third-party OS for the Prizm family. Treat a custom OS as unavailable.

A custom OS would also break your exam plan. Examination Mode ships inside the Casio OS, and the IB approves the Casio build. Your add-in work needs no new OS. You need the Casio OS plus a toolchain on your computer.

03How safe is the official update?

Casio rates a failed update as unlikely, and the steps are short. Follow them in order.

  • Charge the calculator. Casio asks for at least 2 battery bars.
  • Use a Windows or Mac computer. Casio ships no Linux updater.
  • Start the update program first. Connect the calculator only when the program tells you to.
  • Back up your programs and files before you start.

Casio names early connection as a frequent cause of failed updates.

04What if the update fails or the calculator will not start?

The bootloader keeps an emergency OS updater. You start the mode with a key combination plus the RESTART button on the back. The WikiPrizm page on secret key combinations lists the exact keys. Read the page on your computer before an emergency.

Community posts say the emergency mode accepts any official update package, including older ones. Use the updater packaged with the older OS. Several users report repeated failures on one computer and success on an older Windows machine.

Hardware has a limit. In 2016, many fx-CG10 and fx-CG20 units failed in one wave, and the community traced part of the cause to heavy flash writing. Flash the OS rarely.

05Is every change reversible?

Most changes reverse. The OS update does not reverse on paper.

  • Add-ins are .g3a files in the calculator root. Delete the file and the add-in disappears.
  • Copy your programs and files to your computer before every change.
  • Keep a copy of every add-in build, named by version.
  • Keep the OS installer from Casio in your backup folder.
  • Treat the OS update as one way. Older installers exist, but I found no Casio downgrade guide.

Never write code for the OS, bootloader, or flash. Your add-in stays a normal file.

06Will your add-ins run in Examination Mode?

No. The IB Examination Mode locks Memory, Program, eActivity, Python, vector commands, data transfer, and add-in applications. The Casio manual lists 3D Graph as the one add-in exception.

Build for study, projects, and fun. Build nothing for the exam room. Never try to change or bypass Examination Mode.

07How does IB Examination Mode work on the fx-CG50?

Casio offers several modes. Only the mode marked for IB is allowed in IB exams. Casio states Examination Mode 2 is prohibited for the IB.

Casio UK describes the mode as lasting about 12 hours. Reports describe a green frame around the display and a blinking indicator in the top right when the mode runs. Follow the key steps in your Casio manual, and practise once at home with your backup in place. Plan around the 12 hours.

08Which toolchain should you pick?

Pick fxSDK with the gint kernel. The community maintains fxSDK, and gint targets the fx-CG50 directly. fxSDK builds with CMake. fxsdk new makes a project and fxsdk build-cg makes the .g3a file. fxsdk send-cg sends the file with fxlink.

Windows needs WSL Ubuntu, and fxlink does not work inside WSL. Copy the .g3a to the calculator by hand in USB Flash mode.

The older PrizmSDK with libfxcg has a long WikiPrizm tutorial series. Its docs describe quirks: no libc in early versions, and main must never return.

09What should you know before you write code?
  • Add-ins are C or C++ compiled for SuperH. You need a cross compiler.
  • gint adds roughly 50 to 100 KiB to every .g3a.
  • Casio does not document the syscalls. WikiPrizm and gint headers act as your reference.
  • Many CG10 and CG20 add-ins break on the CG50. Write for the CG50 only.
  • One user reported OS 3.80 broke several add-ins. Test on the OS you will keep, which is 3.81.
  • System timers outlive your add-in. A handler pointing at freed memory causes a System Error.
10Where should the coding agent run?

Start in the cloud. The agent writes C, runs native tests, builds the .g3a, and reports compiler errors. None of this needs your calculator. Build the toolchain once in the container image, then reuse the image.

Hardware tests happen on your desk. Download the .g3a, copy the file to the calculator root in USB Flash mode, and run the add-in. A local TUI agent adds little on Windows, because fxlink fails in WSL.

This split is my recommendation. Cloud credits cover long builds and local work stays short.

11How do you make an agent write good fx-CG50 code?

The platform is niche. Models know little about gint and libfxcg. Feed the agent real docs.

  • Add an AGENTS.md with the target, build command, and the rule to never touch OS or bootloader code. A draft sits in the Future spec section.
  • Save the WikiPrizm pages and gint headers into the repo.
  • Ask for one module or screen per task.
  • Keep core logic free of gint calls and run native tests first.
  • Forbid invented syscall names. Every call must match a header in the repo.
  • Review each diff yourself. You flash the file.
12Has anyone used AI to build apps for this platform?

I found no public record of an AI-written fx-CG50 add-in. This reflects my search, not proof.

The closest project is Calc AI, a work in progress. A 2.27 million parameter language model runs on the calculator itself, at about 5.8 tokens per second on stock clocks. The author trained the model in under an hour on one RTX 4060 Ti and ships a .g3a under the MIT license.

Calc AI shows the hardware runs real models. Agents writing add-ins remain undocumented.

13What should you build first?

Build one add-in called Bench with five tools. Start with the shell and the Pacer. The Plan section holds the full spec, milestones, and tests.

Ship each tool as its own tagged version. Test every build on the device.

14Is publishing on Cemetech possible?

Yes, in principle. The Cemetech Archives has a Casio Prizm section for programs and games with .g3a add-ins for the fx-CG50. The upload form failed to load for me, so the exact rules are unconfirmed.

  • Create a Cemetech account and open the upload form from the Archives.
  • Post source code, a readme, and the OS version you tested.
  • State which parts an AI agent wrote.
  • Ask on the Casio forum if a rule is unclear.
  • Planete Casio is a second place to share.
15Should you flash an OS or write add-ins?

Write add-ins. Update the OS only through Casio's official updater.

  • Part one: install Casio 3.81. This meets the IB requirement.
  • Part two: build the add-in as a .g3a file. You delete the file to undo the change.

A custom OS adds risk and gives add-ins nothing. Update first, so you test on the OS you keep.

The product sense transfers. The code does not.

Your habit of shipping small single-purpose tools matches this platform well.

Yes, a subset. Headings, bold, italic, inline code, code blocks, bullets, numbered lists, quotes, rules, and task boxes render. Tables, images, and HTML show as plain text.

A PC script, md2bench.py, cleans your notes before you copy them. The calculator parser stays small. Real bold and italic fonts arrive in a second phase.

- Never write code for the OS, bootloader, or flash.
- Never read, change, or work around Examination Mode.
- Call only functions found in docs/ or the gint headers. Never invent a function name.
- Run native tests and the build before every commit.
- Avoid dynamic allocation inside loops.
- Write files only at session end or on a settings change.
- Add no dependency. Add no feature outside the task.
- Note every storage layout change in CHANGELOG.md.
- Ask the user when a header or doc does not answer a question.

Done means:
- Native tests pass and the build passes.
- You list every screen and every key the task uses.
- You list every file the task reads or writes.
- You list what you could not test without the calculator.
Real fonts for MarkdownPhase B
  • Generate regular, bold, italic, and monospace fonts with fxconv.
  • Swap styles through theme.h. Keep color styling as the fallback.
  • Check glyph coverage for degrees, plus-minus, times, micro, and Greek.
Markdown tablesParked

Render pipe tables as aligned columns. Wrap long cells. Add horizontal scroll only if wrapping fails on real notes.

Game portParked

Pick one of neon-dash or tile-strike after Bench 1.0 ships. Decide screen size, frame rate, and control keys first. Write a one-page design before any code. Keep the game a separate add-in.

Cloud build pipelineParked
  • Container image with the SuperH cross compiler, fxSDK, and gint.
  • Job to run native tests, then build Bench-version.g3a as the artifact.
  • You download the artifact and copy the file to the calculator.
Study import toolParked

Extend md2bench.py to turn a Markdown question list into a Cards file. Reuse your lock-it-in export format when one exists.
